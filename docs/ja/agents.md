# コーディングエージェント

CredShim の後ろで動くコーディングエージェントと、それを用意する人のためのページ。エージェントが持っているもの、リクエストが失敗したときに何が起きたかの見分け方、設定の変更を提案する手順、エージェントへの指示に入れる短い文を載せる。

## エージェントが持っているもの

エージェントから見える API キー、AWS のアクセスキー、SSH エージェントは CredShim のもの。キーはダミーで、多くは `credshim` を含む（`sk-credshim-openai-...` など）。CredShim は、ルールが許す宛先・パス・操作に限って本物のキーに差し替える。推奨構成では本物の値はエージェントの手の届かない所にあるので、ファイルや環境変数を探しても見つからない。

CredShim の失敗は、どれも詳しく見る方法を示す。CredShim が止めた応答は理由と実行するコマンドを返し、`credshim doctor` は失敗したチェックごとにドキュメントを示し、CLI のエラーと `--help` はどれも `credshim docs` のコマンドで終わる。`credshim docs` は、入っているバージョンのドキュメントを、ネットワークも設定も使わずに表示する。

## リクエストが失敗したとき

上から順に見て、最初に当てはまったものに従う。

1. **応答に `credshim-error` ヘッダーがあるか、ボディが `credshim:` で始まる。** CredShim がリクエストを止め、上流へは何も送っていない。1行目が理由。`docs:` はこの種類の拒否を説明するコマンド（`credshim docs troubleshooting#<種類>`）、`details:` はそのリクエストの監査ログの記録をすべて表示するコマンド。推奨構成では `details:` は管理者の権限が要る（`sudo -u` で始まる）ので、実行せずにその行を人に渡す。`limited` は再試行を繰り返さない。`deny` と `not_allowed` は、別のホストや別のキーで回避しない。許可するべきリクエストなら、ルールを変えるよう人に頼む。AWS の SDK と aws CLI では、同じ内容が `CredShim...` のエラーコードのメッセージとして出る。
2. **API 自身がエラーを返し（401、403 など）、応答に `credshim-request-id` はあるが `credshim-error` が無い。** リクエストは CredShim を通り、上流が断った。人にその id を `tail --id` のコマンドで引いてもらう。`inject` なら本物のキーが送られているので、キーの権限かリクエスト自体の問題。`pass` なら、ルールが期待する場所にダミーが無かった（別のヘッダーに入れたなど）。
3. **キーが無効だという 401 で、`credshim-request-id` が無い。** CredShim はこのリクエストを見ていない。ツールがプロキシを通っていない（`HTTPS_PROXY` を見ていないか、このシェルで環境変数を読み込んでいない。`credshim doctor` を実行する）か、そのホストにルールが無くダミーがそのまま送られた（ルールの `host`・`port` を確かめるよう人に頼む）かのどちらか。
4. **ルールのあるホストで TLS の証明書エラーになる。** ツールが開発用の CA を信頼していない。`credshim doctor` を実行する。macOS の Go 製ツールは `credshim docs troubleshooting#go-tools-on-macos` を参照。
5. **SSH が `agent refused operation` と言う。** CredShim のエージェントが、そのホストかユーザーへの署名を断った。`credshim docs ssh` を参照。

## 設定を変えたいとき

推奨構成では、エージェントは設定も秘密も読めず、本物のキーがエージェントを通ってはならない。新しいルール、許可リストの拡大、別のキーが要るときは、エージェントが変更を用意し、人が反映する。エージェントが設定を書き換えられるお試し構成でも、反映は人に任せる。

1. 足すセクションを自分のファイルに書く。よく使う API は `credshim preset <名前>` が出来合いのルールを表示する。それ以外は `credshim docs configuration#writing-rules` を参照。
2. `credshim config check <ファイル>` を実行し、挙がった問題をすべて直す。どの問題にも読む節が付く。
3. 下書き、各キーの行き先の表、`config check` が表示した手順を人に渡す。`!!` の付いた行は必ず指摘する。`secret set` や `aws sso login` などは端末の前の人が打つもので、値をパイプで渡したり端末を偽装したりしない。

## エージェントへの指示に入れる文

プロジェクトの `AGENTS.md` か `CLAUDE.md`（またはエージェント自身の指示）に入れる。

```markdown
## 認証情報（CredShim）

この環境の API キーは CredShim のダミー。CredShim はルールが許す宛先に限って本物のキーに
差し替える。本物のキーを探したり、拒否を回避したりしない。

- `credshim-error` ヘッダーがあるか、ボディが `credshim:` で始まる応答は CredShim が止めたもの。
  1行目を読み、`docs:` のコマンドを実行する。`limited` は再試行を繰り返さない。
  `details:` のコマンドが `sudo` で始まるなら、私に実行を頼む。
- ツールが繋がらない、または証明書エラーになるときは `credshim doctor` を実行する。
- CredShim のルールを変えたいときは、下書きを書いて `credshim config check <ファイル>` で確かめ、
  下書きと表示された手順を私に渡す。
- `credshim docs` で、このバージョンの CredShim のドキュメントを読める。
```
